# Beat the Deck｜測試計畫

版本 0.1（2026-10-06）。搭配 `SPEC.md` 讀。這份文件列出**要先寫的測試**；實作的目的是讓它們通過。

2026-10-06 依實作中證實的問題訂正了幾處，每一處都標了「訂正」，並寫出原文與原因；沒標的都是原本的內容。

## 1. 做法

每個任務固定四步：

1. **紅**：照這份文件把測試寫出來，跑一次，確認是失敗的（而且是因為功能還不存在而失敗，不是因為測試寫錯）。
2. **綠**：寫最少的實作讓它通過。
3. **整理**：重構，測試保持綠。
4. **檢查**：`npm run check` 全綠才算完成。

`npm run check` ＝ `tsc --noEmit` ＋ `eslint` ＋ `vitest run`（單元、契約、AI）。端到端測試另外用 `npm run e2e` 跑，CI 上也跑。

## 2. 五層測試

| 層 | 放哪 | 測什麼 | 誰寫 |
|---|---|---|---|
| 單元 | 與原始碼同資料夾的 `*.test.ts` | core、ai、shell 裡純的部分 | T1–T4 |
| 契約 | `tests/contract/` | 登記表裡**每一張牌**自動跑同一組檢查 | T2 寫一次，之後每張牌自動被測 |
| 規則 | `src/games/<id>/logic.test.ts` | 那張牌自己的規則 | 做那張牌的任務 |
| AI 行為 | `tests/ai/` | 性格與等級的統計性質 | T3 寫框架，每張牌加自己的門檻 |
| 端到端 | `tests/e2e/` | 真的在瀏覽器裡開得起來、玩得完一局 | T4 |

所有用到亂數的測試都用固定的種子清單，不可以有偶爾才失敗的測試。統計測試的種子清單固定為 `0..N-1`。

## 3. 單元測試（先寫）

### 3.1 `core/rng`

- 同一個種子，前 1000 個 `next()` 完全相同。
- 不同種子（0 與 1），前 10 個值不全相同。
- `next()` 的值都在 `[0, 1)`；10 萬個樣本的平均在 0.49 到 0.51 之間。
- `int(n)` 的值都是 `[0, n)` 的整數；`int(6)` 抽 6 萬次，每一面出現 9,500 到 10,500 次。
- `fork('a')` 兩次得到相同的序列；`fork('a')` 與 `fork('b')` 的序列不同。
- 呼叫 `fork` 不影響母亂數接下來的輸出。

### 3.2 `core/hash`

- 同樣內容的兩個物件（鍵的順序不同）雜湊相同。
- 任何一個數值欄位差 1，雜湊不同。
- state 裡有 `NaN`、`undefined`、函式時丟出錯誤，訊息要指出是哪個欄位。

### 3.3 `core/match` 與 `core/replay`

用一個測試專用的小遊戲 `tests/fixtures/counter-game.ts`（每個 tick 按著 a 的那一邊加 1 分，100 tick 結束）。

- 兩個都不按的控制器：分數 `[0, 0]`，`winner` 是 `null`，`ticks` 是 100。
- 一邊一直按 a：那一邊 100 分並且獲勝。
- `playMatch` 回傳的 `inputs` 長度等於 `ticks`。
- 把回傳的 `inputs` 交給 `replay(game, seed, config, inputs)`：`finalHash` 與原本相同。
- 改掉 `inputs` 裡 side 0 或 side 1 的 a 鍵（開頭、中段、結尾各測一個 tick）：`finalHash` 不同。
  - 訂正（2026-10-06）：原文是「改掉 `inputs` 裡任一個 tick 的一顆按鍵」。但上面定義的 counter-game 只有 a 鍵會進入 state，改 b 或方向鍵不可能改變 `finalHash`，照字面做不出來。b 與方向鍵由契約測試 K1、K10 對真的牌涵蓋（它們用完整的隨機按鍵跑決定性與重播）；那兩條驗的是「同樣輸入得到同樣結果」，不是「每顆按鍵都會改變雜湊」。
- 遊戲在 `maxTicks` 之前就 `isOver`：`playMatch` 立刻停，不多走。
- 遊戲到了 `maxTicks` 還沒 `isOver`：`playMatch` 丟出錯誤（這代表遊戲違反契約）。

### 3.4 `shell/loop`

把「真實時間」當參數傳進去，測試裡用假的時鐘。

- 跨幀累計經過 1000 毫秒（拆成多幀送進去，例如 100 幀 × 10 毫秒）：加總剛好推進 60 個 tick。
  - 訂正（2026-10-06）：原文是「經過 1000 毫秒：剛好推進 60 個 tick」。如果那 1000 毫秒是一幀送來的，下面「一幀最多推進 5 個 tick」的上限會讓它永遠湊不到 60，兩條互相卡住；所以「經過 1000 毫秒」讀成跨幀的累計時間。
- 一幀經過 16.67 毫秒：推進 1 個 tick；經過 8 毫秒：這一幀推進 0 個，下一幀補上。
- 一幀經過 5000 毫秒（分頁切回來）：最多推進 5 個 tick，多的丟掉。
- 暫停時不推進。

### 3.5 `shell/input`

- 鍵盤按下方向鍵與 WASD 都對應到相同的抽象鍵。
- 同時按左與右：兩個都是 true（由遊戲自己決定怎麼處理）。
- 視窗失去焦點：所有鍵變成放開。
- C-2 用的方向轉換：`rotateButtons(buttons, r)` 對 `r = 0, 1, 2, 3` 各測四個方向，a 與 b 不受影響；轉四次回到原樣。

### 3.6 `shell/progress`

- 沒有存檔：回傳預設值（全部沒翻開、等級 1）。
- 存檔是壞掉的 JSON、或版本號不認得：回傳預設值，不丟錯。
- 解鎖規則：四張 A 一開始開放；贏了 `C-A` 之後 `C-2` 開放、`C-3` 還沒；翻開 13 張後 `JK-R` 開放；翻開 40 張後 `JK-B` 開放。
- 全域等級：翻開 0、1、2 張是 1；翻開 3 張是 2；翻開 27 張以上是 10。
- 某張牌的實際等級 ＝ 夾在 1 到 10 之間的（全域等級 ＋ 這張牌的基礎等級 − 1）。

### 3.7 `ai/level`

- 等級 1 與 10 的四個參數等於 SPEC 第 7.2 節表格的值。
- 等級 1 到 10，`reactionTicks`、`decideEvery`、`epsilon` 單調不增，`depth` 單調不減。
- 包上等級之後的控制器：在 `decideEvery = 12` 時，連續 12 個 tick 回傳同一組按鍵。
- `reactionTicks = 18` 時，控制器在第 t 個 tick 拿到的是第 t−18 個 tick 的 state（用 counter-game 加一個會記錄收到什麼 state 的假性格來驗證）。
- `epsilon = 0` 時完全等於底層性格的決定；`epsilon = 1` 時回傳的一定是 `actions()` 裡的某一個。

### 3.8 純度檢查

- 一個測試讀取 `src/core/**`、`src/ai/**`、`src/games/**/logic.ts` 的原始碼文字，出現 `Math.random`、`Date.now`、`performance.now`、`window`、`document`、`setTimeout`、`setInterval` 任何一個就失敗，訊息列出檔名與行號。

## 4. 契約測試（T2 寫一次，對每張牌自動跑）

`tests/contract/all-games.test.ts` 用 `describe.each(registry)`。新增一張牌不用改這個檔案。

對每張牌、種子 0 到 19：

| 編號 | 檢查 | 通過標準 |
|---|---|---|
| K1 | 決定性 | 同樣的種子與同一串隨機輸入跑兩次，每 60 tick 比一次雜湊，全部相同 |
| K2 | 可序列化 | 每 60 tick 做一次 `JSON.parse(JSON.stringify(state))`，雜湊不變 |
| K3 | 沒有壞數字 | state 裡沒有 `NaN`、`Infinity`、`undefined` |
| K4 | step 是純的 | 呼叫 `step` 前先深度凍結 state，不可以丟出錯誤；呼叫前後原 state 的雜湊相同 |
| K5 | 會結束 | 兩個隨機控制器，在 `maxTicks` 之內 `isOver` 變成 true |
| K6 | 結束後穩定 | `isOver` 之後再 `step` 60 次，`score` 與 `winner` 不變 |
| K7 | 分數一致 | `winner` 不是 null 時，那一邊的分數不低於另一邊（有淘汰規則的牌在 `meta.ts` 標 `winnerNotByScore: true` 可以跳過這條） |
| K8 | 動作合法 | 每個 tick `actions()` 至少回傳一個；兩邊都是 |
| K9 | 評估可用 | `evaluate()` 的 `danger` 在 0 到 1 之間，`gain` 是有限的數 |
| K10 | 重播 | `playMatch` 的結果用 `replay` 重跑，`finalHash` 相同 |
| K11 | 夠快 | 不開畫面跑一場完整對局（兩個等級 5 的預設性格），在 CI 上少於 2 秒 |
| K12 | 對稱（只對 `meta.symmetric: true` 的牌） | 兩邊用同一個性格與等級，200 個種子，任一邊的勝率在 40% 到 60% 之間 |

另外對 `render`：

| 編號 | 檢查 | 通過標準 |
|---|---|---|
| R1 | 不改 state | 對凍結的 state 呼叫 `render`（用假的 2D context）不丟錯 |
| R2 | 只用色盤 | 假的 context 記錄所有 `fillStyle` 與 `strokeStyle`，都在 16 色色盤裡 |
| R3 | 不畫出界 | 所有繪圖呼叫的座標都在 0..320 × 0..240 之內（可以有 8 像素的容許） |

與 `meta`：id 與資料夾名稱一致、花色與點數與 id 一致、有名稱、有一句說明、有操作說明、`docs/cards/<id>.md` 存在。

## 5. AI 行為測試

框架在 `tests/ai/harness.ts`：`winRate(game, policyA, levelA, policyB, levelB, seeds)` 回傳 A 的勝率（平手算半場）。

### 5.1 對每張牌都要成立（放進契約測試的迴圈，200 個種子）

| 編號 | 檢查 | 門檻 |
|---|---|---|
| A1 | AI 比亂按強 | 這張牌的預設性格、等級 5，對 `random`：勝率至少 75% |
| A2 | 等級有意義 | 預設性格等級 9 對等級 2：勝率至少 60% |
| A3 | 人打得贏第一級 | `human-model` 對預設性格等級 1：勝率至少 45% |
| A4 | 人打不太贏第十級 | `human-model` 對預設性格等級 10：勝率最多 35% |
| A5 | 決策夠快 | 預設性格等級 10 的 `decide()`，平均每次少於 1 毫秒，第 99.9 百分位少於 8 毫秒（樣本數至少 18,000；訂正見下） |

> 訂正（2026-10-06）：A5 原文是「最慢一次少於 8 毫秒」，現在改成「p99.9 少於 8 毫秒，而且樣本數至少 18,000」（種子從 0 往上加到湊滿，最多 200 個）。這是使用者核准的改動：整套測試平行跑時，最慢的那幾次量到的是 GC 暫停與排程被搶，不是演算法本身；p99.9 排除最慢的 18 個。平均少於 1 毫秒沒有動。

紅心的牌運氣成分高，A1 的門檻降為 60%、A2 降為 55%；要在那張牌的 `meta.ts` 用 `luckHeavy: true` 標明。鬼牌不跑這一節。

> 訂正（2026-10-08）：A4 對「純反射牌」不適用。原文的 A4 門檻（≤35%）沒有動。這是老闆的裁示（GOAL 第 1 條優先）：`src/ai/level.ts` 的 `reactionTicks` 已對所有等級固定成 12 tick（與人類模型相同，見 `docs/DESIGN-AI-FUN.md` 9.7），沒有策略深度可以剝削的牌，等級 10 要把人類模型壓在 35% 以下只能靠超人類的反應，那正是 GOAL 第 1 條明文不要的。所以 `CardMeta` 多一個選用旗標 `reflexOnly: true`（`src/games/types.ts`），只有核准的四張掛：**S-3 擦彈、S-7 拔槍、S-J 射手與靶、S-Q 鏡像**。

> - 沒有策略深度才能掛。有路徑搜尋之類真策略的牌（梅花、D-2）不能用旗標蓋掉 A4：那是把問題貼標籤。新增掛旗標的牌要老闆核准，`registry-meta.test.ts` 的清單就是核准的清單。

## 6. 第一批十二張牌的規則測試

每一條是一個測試。用「直接構造 state」的方式測（每張牌提供 `makeState(overrides)` 測試輔助函式），不要靠跑很多 tick 碰運氣。

### C-A 貪食蛇對決

1. 初始：兩條蛇長度 3，位置與方向如規格；場上 2 個食物，不在蛇身上。
2. 6 個 tick 後蛇頭前進一格；第 1 到 5 個 tick 不動。
3. 往右走時按左：方向不變。按上：下一次移動改成往上。
4. 一格之內連按上再按左（原本往右）：只採用第一個有效的轉向，不會變成掉頭。
5. 蛇頭走進食物：分數加 1、長度加 1、那個食物消失並在空格補一個，場上仍是 2 個。
6. 撞牆：那條蛇死亡，`isOver`，另一邊是 `winner`。
7. 撞自己的身體、撞對方的身體：同上。
8. 兩條蛇同一個 tick 頭對頭：都死，分數高的贏；同分 `winner` 是 `null`。
9. 走進對方剛離開的尾巴那一格：不算撞（尾巴已經移走）。
10. 3600 tick 到：`isOver`，分數高的贏。
11. 場地滿到沒有空格可以放食物：不當掉，場上食物數可以少於 2。

### C-2 旋轉的房間

1. C-A 的 11 條在這張牌上全部成立（共用同一組測試）。
2. `viewRotation` 在第 0 到 599 tick 是 0，600 到 1199 是 1，依此類推，每 2400 tick 循環。
3. 旋轉前 60 tick，state 的 `warning` 是 true。
4. 給 `step` 的輸入是世界方向：不管 `viewRotation` 是多少，輸入「上」蛇就往世界的上走。（畫面方向到世界方向的轉換在 `shell`，由 3.5 節的測試涵蓋。）
5. AI 的 `evaluate` 與 `actions` 不受 `viewRotation` 影響。

### C-3 紅藍食物

1. 初始：紅、藍各 2 個。
2. 吃到正確顏色：加 1 分、長度加 1。
3. 吃到錯誤顏色：扣 2 分、長度不變；分數可以是負的。
4. 吃掉之後補的是同一種顏色，場上維持各 2 個。
5. 正確顏色每 480 tick 換一次；換之前 90 tick `warning` 是 true。
6. 在換顏色的同一個 tick 吃到食物：用換之前的顏色判定。
7. 撞擊規則與 C-A 相同（共用測試 6 到 9）。

### S-A 落雨

1. 兩個場地在任何 tick 的子彈位置完全相同。
2. 按右：每 tick x 加 1.5；同時按右與上：斜向移動，速度仍是 1.5（不是 1.5×√2）。
3. 按住 a：速度變成 0.6。
4. 走到場地邊緣：停在邊緣，不出界。
5. 子彈與玩家的中心距離小於 5（3＋2）：命中數加 1，那顆子彈消失。
6. 命中後 60 tick 內再碰到子彈：不算，子彈也不消失。
7. 子彈離開下緣：從 state 移除（陣列不會無限長）。
8. 生成間隔：第 0 tick 附近每 20 tick 一顆，第 3600 tick 附近每 5 tick 一顆；全場總數在預期值的正負 2 顆之內。
9. 分數是負的命中數；命中數少的贏。
10. 都不動的兩邊：命中數相同，平手。

### S-2 瞄準彈

1. 一般子彈每 15 tick 一顆。
2. 每 45 tick 一顆瞄準彈；兩個場地的生成位置相同。
3. 瞄準彈的速度向量指向該場地玩家在生成當下的位置，大小 1.6。
4. 玩家在生成之後移動：瞄準彈不轉彎。
5. 兩邊玩家位置不同時：兩個場地的瞄準彈方向不同。
6. 玩家剛好在生成點正下方：方向是正下，不會除以零。
7. S-A 的 2 到 7、9 成立。

### S-3 擦彈

1. 子彈與玩家距離小於 10 且沒有命中：擦彈數加 1。
2. 同一顆子彈在範圍內停留很多 tick：只算一次。
3. 同一顆子彈先擦彈後命中：擦彈算 1 次，命中也算。
4. 無敵期間經過的子彈：不算擦彈。
5. 分數 ＝ 擦彈數 − 5 × 命中數。
6. 站著不動被打中 2 次、擦彈 3 次：分數是 −7。

### D-A 搶金幣

1. 牆的生成：同一個種子同一組牆；所有空格連通（對種子 0 到 99 用洪水填充驗證）。
2. 兩個起始格都不是牆。
3. 每 5 個 tick 最多走一格；朝牆走：不動。
4. 走到金幣格：分數加 1，在隨機空格補一枚，場上維持 6 枚。
5. 兩個角色同一個 tick 走到同一枚：各加 1 分，只補一枚。
6. 兩個角色可以站在同一格。
7. 補的金幣不會出現在牆上，也不會出現在已經有金幣的格子。
8. 3600 tick 到：分數高的贏。

### D-2 背包上限

1. 撿金幣：背包加 1，分數不變。
2. 背包已經 3 枚時走到金幣格：金幣留在原地。
3. 走到自己的基地：分數加上背包的數量，背包歸零。
4. 走到對方的基地：什麼都不發生。
5. 背包是空的走到基地：什麼都不發生。
6. 時間到時背包裡有 2 枚：不算分。
7. D-A 的 1 到 3、6、7 成立。

### D-3 會貶值的寶石

1. 寶石出現時價值 9。
2. 每 60 tick 減 1：出現後第 59 tick 還是 9，第 60 tick 是 8，第 480 tick 是 1。
3. 價值到 1 之後不再降；再過 120 tick 消失，並補一顆新的。
4. 撿到：分數加上當下的價值。
5. 場上維持 5 顆。
6. 在寶石減值的同一個 tick 撿到：拿到減之前的價值。
7. D-A 的 1 到 3、6 成立。

### H-A 貪心骰

1. 人先。輪到人時 AI 的輸入被忽略，反之亦然。
2. 按 a 擲到 2 到 6：回合累積增加那個點數，還是自己的回合。
3. 按 a 擲到 1：回合累積歸零，換對方。
4. 按 b：回合累積加進總分，換對方。
5. 回合累積是 0 時按 b：允許，總分不變，換對方。
6. 輪到自己 300 tick 沒按：自動當成按 b。
7. 按住 a 不放：只擲一次（要放開再按才算下一次）。
8. 人先到 50：AI 還有一個回合；AI 在那個回合追過：AI 贏。
9. AI 先到 50（AI 是後手）：立刻結束。
10. 兩邊各 20 個回合後都沒到 50：比總分。
11. AI 做每個決定前等 45 tick。
12. 用固定種子，骰子序列是決定的。

### H-2 引信

1. 一局開始，按住 a：累積每 tick 加 1。
2. 放開：累積加進總分，這一局對自己結束，再按沒有作用。
3. 累積的 tick 數達到引信長度：爆炸，這一局得 0。
4. 開始後 60 tick 內沒按：這一局得 0。
5. 兩邊同一局的引信長度相同。
6. 引信長度在 120 到 600 之間（對 1000 個種子驗證範圍；平均在 340 到 380 之間）。
7. 一邊已經結束、另一邊還按著：局還沒結束。
8. 兩邊都結束：state 裡這一局的引信長度變成公開，然後進下一局。
9. 5 局結束：`isOver`，總分高的贏。
10. 剛好在達到引信長度的同一個 tick 放開：算爆炸。

### H-3 懸崖

1. 不煞車：一定掉下去，這一局 0 分。
2. 速度每 30 tick 加 0.1。
3. 按下 a 之後：每 tick 速度減 0.05，到 0 為止；之後放開或再按都沒有作用。
4. 停下的位置是 287.6：得 287 分。
5. 停下的位置剛好是 300.0：得 300 分。超過 300：0 分。
6. 兩邊同一局的起始速度相同，在 0.8 到 1.2 之間。
7. 煞車距離的公式與模擬結果一致（對 5 個起始速度驗證，誤差小於 1 像素）。
8. 5 局結束比總分。

## 8. CI

GitHub Actions，一個流程檔：

| 步驟 | 內容 |
|---|---|
| check | `npm ci`、`npm run check` |
| e2e | `npx playwright install --with-deps chromium`、`npm run e2e` |
| deploy | 只在 `main`：`npm run build`，發布到 GitHub Pages |

`npm run check` 的總時間目標：54 張牌都完成時少於 5 分鐘。超過的話把 5.1 節的種子數從 200 降到 100，並在 PR 說明裡寫明。

> 訂正（2026-10-06）：現況與原文的假設不同。
> - 上面的授權已經動用了：`tests/ai/seeds.ts` 的 `AI_SEED_COUNT` 現在是 100（5.1 節標題寫的 200 是降之前的數字；K12 的 200 個種子沒動）。
> - 但降了以後，13 張牌的 `npm run check` 仍要約 220 秒，外推 54 張約 800 到 900 秒（推論：照張數線性外推，每張牌的成本其實不同），遠超過 5 分鐘。所以只降種子數不足以達標，還需要別的手段。
> - 可選的手段（還沒決定，由使用者選）：優化模擬（讓慢的牌的 `step`／`evaluate` 更快）、把 CI 上的 `npm run check` 拆成幾個 job 平行跑、換核心更多的 runner、調整這個 5 分鐘的目標。
